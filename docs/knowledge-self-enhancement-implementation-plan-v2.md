# 知识自生长与趋势决策支持系统实施计划

## 1. 目标与边界

### 1.1 最终目标

将网页爬取、外部导入和人工输入的资料，转化为带证据、可追溯、可复用、可持续迭代的知识资产，并通过时间变化和历史验证辅助趋势判断。

系统最终应形成以下闭环：

```text
资料采集/导入
    -> 原始文档入库
    -> 结构化知识声明提取
    -> 证据校验、去重、冲突检测
    -> 跨文档关联
    -> LLM生成知识综合文档
    -> 审核/质量门控
    -> 回灌知识库和检索索引
    -> 趋势信号与预测
    -> 预测结果回测
    -> 反馈下一轮知识增强
```

### 1.2 明确边界

LLM负责：

- 归纳、对比、解释和提出候选假设
- 从资料中提取结构化知识声明
- 生成面向人的研究简报和决策摘要

规则、数据库和统计模型负责：

- 来源、版本和证据保存
- 去重、冲突和状态管理
- 时间序列统计
- 预测结果评估

LLM生成的推断不能未经审核直接升级为事实。

## 2. 当前系统复用与改造判断

### 2.1 可以复用

- `Article`：继续作为原始资料文档
- Neo4j：继续保存实体、知识声明和关系
- `LLMService`：继续作为模型调用入口
- 现有知识点页面和 API：作为候选知识浏览入口
- 现有定时爬取：只负责采集和入库

### 2.2 必须改造

- `self_enhancement.py`：从单篇文章抽取器改为可恢复的流水线
- 知识点模型：增加证据、来源、版本、状态和模型信息
- 关联发现：从单文章关键词关联改为全库候选关联
- `prediction.py`：从节点数量演示逻辑改为时间序列和可回测预测
- 任务机制：从内存任务改为数据库持久化任务和可重试 Worker
- 知识输出：新增可持久化的知识综合文档，而不是只返回临时 summary

## 3. 核心数据模型

建议先使用 PostgreSQL 保存任务、版本和审核状态，Neo4j 保存知识关系，原始正文继续存放在文章表或对象存储中。

### 3.1 原始文档 `source_documents`

可复用现有 `articles`，补充或统一以下字段：

- `id`
- `source_type`：web、wechat、file、manual
- `source_url`
- `title`
- `content`
- `published_at`
- `content_hash`
- `source_reliability`
- `language`
- `created_at`

### 3.2 知识声明 `knowledge_claims`

知识声明是最小可复用单位，不直接等同于文章摘要。

- `id`
- `claim_text`
- `claim_type`：fact、opinion、method、definition、hypothesis、signal
- `subject`
- `predicate`
- `object`
- `valid_from`
- `valid_to`
- `confidence`
- `status`：candidate、approved、rejected、deprecated
- `content_hash`
- `created_at`
- `updated_at`

### 3.3 证据 `claim_evidence`

每条重要知识声明至少关联一条证据。

- `claim_id`
- `document_id`
- `quote`
- `section_or_offset`
- `source_url`
- `published_at`
- `evidence_type`：direct、inferred、contradictory
- `support_score`

### 3.4 知识关系 `knowledge_relations`

- `source_claim_id`
- `target_claim_id`
- `relation_type`
- `strength`
- `evidence_ids`
- `status`
- `created_at`

### 3.5 知识综合文档 `knowledge_syntheses`

- `id`

- `content`

- `topic`
- `source_document_ids`
- `source_claim_ids`
- `included_relation_ids`
- `iteration`
- `parent_synthesis_id`
- `model_name`
- `prompt_version`
- `quality_score`
- `status`：draft、review、approved、published、archived
- `created_at`
- `updated_at`

### 3.6 处理任务 `knowledge_jobs`

- `id`
- `job_type`
- `target_id`
- `input_hash`
- `pipeline_version`
- `status`
- `retry_count`

### 3.7 预测记录 `forecasts`

- `id`
- `topic`

- `confidence_interval`
- `factors`
- `source_claim_ids`

- `created_at`
- `actual_value`
- `evaluation_status`
- `error_metric`

## 4. 知识状态和升级规则

所有知识都必须经过状态流转，不能直接覆盖旧记录：

```text
candidate -> review -> approved -> published -> deprecated
                 \-> rejected
```

### 4.1 自动通过条件

只有满足以下条件，才允许自动发布：

- 至少一个可信来源
- 有原文引用
- 与已有知识不冲突，或冲突已明确标记
- 内容不是纯摘要，而是可复用的定义、规律、方法或结论
- 置信度和来源质量达到阈值
- 未命中高风险主题规则

### 4.2 必须人工审核的情况

- 只有单一低可信来源
- LLM提出的因果关系
- 预测性结论和投资、政策、医疗等高风险内容
- 多来源之间存在冲突
- 结论明显超出原文证据
- 需要写入正式知识库的假设或趋势判断

## 5. 分阶段实施

## 阶段 0：基线和可观测性

### 目标

确认现有知识点、关联和预测功能的真实运行状态，建立改造前基线。

### 工作内容

- 统计文章数量、知识点数量、重复率和空关联率
- 记录当前 LLM 调用成功率、降级次数和平均耗时
- 记录每次知识处理的输入哈希和结果
- 为现有接口增加明确的日志和错误分类
- 区分“处理成功”和“内容质量通过”

### 验收标准

- 能回答任意知识点来自哪些文章和哪些原文段落
- 能统计 LLM 抽取失败和规则降级次数
- 能统计知识点重复、孤立和未审核数量
- 不修改现有数据含义，不直接清理历史数据

## 阶段 1：知识声明和证据链

### 目标

把当前 `KnowledgePoint` 升级为带证据的候选知识声明。

### 工作内容

- 长文档按段落或 token 分块
- LLM 输出结构化 JSON
- Pydantic 严格校验
- 每条声明保存原文引用和位置
- 保存模型、提示词版本和输入哈希
- LLM失败时标记任务失败或低质量，不静默伪装为正常结果
- 保留现有知识点 API，增加兼容字段

### 验收标准

- 任意知识声明可以定位到原文
- 重复执行相同文档不会无限创建重复声明
- 同一文档内容未变化时支持幂等跳过
- 结构化输出失败可以重试并留下失败原因

## 阶段 2：跨文档去重、合并和冲突检测

### 目标

让知识库能够积累，而不是每篇文章都产生孤立知识点。

### 工作内容

- 先用标题、关键词和哈希做精确去重
- 再用向量或全文检索召回相似声明
- 对候选声明执行同义合并判断
- 识别支持、冲突、补充和演化关系
- 保留多个来源，不覆盖旧声明
- 对冲突知识进行并列展示

### 验收标准

- 相同事实来自多篇文章时合并为一个知识主题
- 不同来源的支持证据可以累积
- 冲突观点不会被静默覆盖
- 关联结果必须能显示证据来源

## 阶段 3：知识综合文档和回灌

### 目标

真正实现“LLM产出可复用内容，再放回知识库”。

### 工作内容

- 根据主题、时间范围和相关声明召回上下文
- LLM生成结构化综合文档
- 文档必须包括：结论、证据、共识、分歧、变化、未知项、待验证假设
- 保存来源文档和声明 ID
- 生成草稿并进入审核队列
- 审核通过后写入 `knowledge_syntheses`
- 将综合文档加入全文或向量检索
- 将综合文档关联回 Neo4j

### 验收标准

- 综合文档不是单篇文章摘要
- 通过来源 ID可以还原生成依据
- 删除或废弃来源后可以定位受影响的综合文档
- 综合文档可被下一轮增强流程检索到

## 阶段 4：可靠的异步处理流水线

### 目标

让长时间、批量和定时任务可以恢复、重试和限流。

### 工作内容

- 增加持久化 `knowledge_jobs`
- 采集任务和知识增强任务解耦
- 支持任务去重、租约、超时和重试
- 限制同时运行的 LLM 任务数
- 服务重启后恢复 pending/running 任务
- 对单文档失败不影响整个批次
- 增加人工重跑和取消接口

### 推荐流程

```text
定时爬取 -> 原始文章入库 -> 创建增强任务 -> Worker处理 -> 审核/发布
```

不要在爬取请求或实体抽取流程中直接 `create_task` 启动完整增强链路。

### 验收标准

- 服务重启后任务状态不丢失
- 同一输入不会并发重复处理
- 失败任务可以自动重试和人工重试
- 能看到每一步耗时和失败原因

## 阶段 5：知识关联升级

### 目标

从单文章关键词关联升级为全库语义和证据关联。

### 工作内容

- 保留关键词关联作为候选召回
- 增加跨文章全文或向量检索
- 对高相似候选调用 LLM 判断关系类型
- 增加时间关系和冲突关系
- 对关系设置状态和证据
- 评估图谱中的孤立节点、重复节点和高价值桥接节点

### 验收标准

- 新知识可以关联历史知识
- 关联不是只依赖关键词相同
- 每条重要关系都有证据
- 关系错误可以人工修正

## 阶段 6：趋势信号和趋势分析

### 目标

先做可解释的趋势分析，再做预测，不直接把 LLM 输出称为预测。

### 趋势信号

按主题和时间窗口统计：

- 相关文档数量变化
- 可信来源数量变化
- 关键词和实体出现频率
- 支持观点与反对观点数量
- 新增关系数量
- 来源情绪或立场变化
- 知识声明的首次出现和最近更新时间

### 趋势分析输出

- 当前状态
- 变化方向
- 变化速度
- 主要驱动因素
- 证据来源
- 不确定性
- 需要持续观察的指标

### 验收标准

- 趋势方向来自真实历史数据
- 每个趋势结论可以回溯到指标和来源
- 支持按 7、30、90 天窗口比较
- 没有足够数据时明确返回“数据不足”

## 阶段 7：可回测趋势预测

### 目标

只有具备历史数据和回测能力后，才提供正式预测。

### 工作内容

- 明确定义预测目标，例如文档数量、热度、事件概率或指标值
- 保存每次预测，不覆盖历史预测
- 支持 7、30、90 天预测窗口
- 先使用简单基线模型，再与更复杂模型比较
- LLM负责解释影响因素，不直接负责未经验证的数值预测
- 到期后自动写入实际值并计算误差
- 维护不同主题和时间窗口的历史表现

### 验收标准

- 至少有一个可重复的基线模型
- 预测结果有实际值对照
- 能查看误差和历史表现
- 数据不足时不生成虚假的置信度
- 页面明确区分“趋势分析”和“正式预测”

## 阶段 8：决策支持和反馈闭环

### 目标

让系统真正辅助决策，而不是只展示知识图谱。

### 工作内容

- 支持用户收藏主题和关注指标
- 自动生成周期性研究简报
- 对新资料标记“新增、变化、冲突、风险”
- 用户可以对知识和预测进行确认、否定或补充
- 将反馈用于调整来源权重、提示词和阈值
- 保留人工决策记录，不把用户意见直接当成事实

### 验收标准

- 用户能看到一个主题最近发生了什么变化
- 能看到变化的证据和不同观点
- 能看到系统为什么给出当前判断
- 能查看历史预测是否准确
- 能对结果进行反馈并影响后续排序

## 6. 知识综合文档的固定输出格式

每次生成的综合文档建议固定为：

```text
# 主题

## 一句话结论

## 当前共识

## 关键证据

## 近期变化

## 不同来源的分歧

## 可复用知识

## 推断与假设

## 可能的趋势信号

## 仍需验证的问题

## 来源和证据索引
```

其中“可复用知识”和“推断与假设”必须分开保存。

## 7. 质量指标

### 知识质量

- 证据覆盖率
- 来源可追溯率
- 重复率
- 冲突识别率
- 人工采纳率
- 人工驳回率

### 流程质量

- LLM成功率
- 结构化解析成功率
- 平均处理时长
- 任务重试率
- 任务丢失率
- 单篇成本

### 预测质量

- MAE/RMSE
- 方向判断准确率
- 置信区间覆盖率
- 不同主题的稳定性
- 预测提前量

没有这些指标时，系统只能算知识整理工具，不能算决策支持系统。

## 8. 推荐的最小可用版本

第一版不要同时实现所有功能，建议只交付以下闭环：

1. 选择一篇文章或导入一份文档
2. 分块提取带原文引用的知识声明
3. 与已有知识进行重复和冲突检测
4. 生成一份带来源的知识综合文档
5. 进入审核状态
6. 审核通过后回灌知识库
7. 可以按主题检索这份综合文档
8. 保存全流程任务记录

第一版暂不承诺正式趋势预测，只提供趋势信号和证据摘要。

## 9. 发布门槛

满足以下条件才进入自动化运行：

- 任务持久化和重启恢复通过
- 相同输入幂等处理通过
- 关键知识可追溯到原文
- LLM结构化输出失败可识别
- 重复和冲突不会静默覆盖
- 综合文档可以重新检索
- 低质量结果不会自动发布
- 趋势分析结论有指标和来源
- 预测功能具备至少一轮历史回测

## 10. 实施原则

- 先保证证据和可追溯，再追求自动化
- 先做知识综合，再做自我循环
- 先做趋势分析，再做趋势预测
- 先做可恢复任务，再提高并发量
- 允许系统输出“数据不足”或“不确定”，不要强行生成结论
- 所有自动生成内容都保留版本，禁止覆盖原始资料

## 11. 与现有功能的关系和归并方案

本项目不再新增一套与现有文章、知识图谱和搜索系统平行的系统。后续所有功能必须明确归属，并优先改造现有模块。

### 11.1 现有功能归属

| 现有功能 | 继续保留 | 后续职责 | 处理方式 |
|---|---:|---|---|
| 爬取和外部导入 | 是 | 只负责获取原始资料 | 不在采集流程中直接生成正式知识 |
| `Article` 文章库 | 是 | 原始文档和来源资料 | 作为所有知识声明的来源，不与综合文档混用 |
| `Article.summary` | 是 | 单篇文章阅读摘要 | 只服务文章列表和快速浏览，不作为正式知识 |
| `kg_sync.py` | 是 | 原始文章同步到知识图谱、维护实体状态 | 保留实体抽取职责，移除其中的自增强业务逻辑 |
| `extractor.py` | 是 | 从单篇文章提取基础实体和关系 | 不负责跨文档知识综合 |
| `graph.py` | 是 | Neo4j连接、实体、关系和图查询 | 扩展知识声明和综合文档节点，不另建图服务 |
| `self_enhancement.py` | 改造 | 编排知识声明、关联、综合和审核任务 | 移除内存任务和临时 summary 逻辑 |
| `KnowledgePoint` | 过渡保留 | 兼容现有页面和历史数据 | 逐步映射为 `knowledge_claim`，不再新增第二套含义相同的节点 |
| `Association` | 改造 | 保存知识声明之间的有证据关系 | 统一由 `knowledge_relations` 管理 |
| `embedding.py` | 条件保留 | 为知识声明和文档提供语义召回 | 先确认向量数据库部署，再接入去重和召回 |
| `prediction.py` | 保留入口、重写核心 | 趋势分析和可回测预测 | 不再依据实体数量生成预测 |
| `prompt_templates.py` | 保留并版本化 | 管理结构化提取、综合和分析提示词 | 每次产物记录 prompt 版本 |
| `event_listener.py` | 归并 | 只发布知识任务事件 | 不直接调用完整增强流程 |
| 自增强前端页面 | 保留并调整 | 统一展示任务、候选知识、综合文档、审核和趋势 | 不再单独展示没有持久化依据的统计数字 |

### 11.2 不再新增的功能

后续实施中明确不新增以下平行功能：

- 不新增第二个文章表来保存综合文档；综合文档使用独立的知识产物模型，并通过来源字段关联 `Article`
- 不新增第二套 Neo4j 客户端或图谱服务；统一复用 `graph.py`
- 不新增第二套 LLM 客户端；统一复用 `LLMService`
- 不新增单独的“摘要库”；文章摘要、知识声明和综合文档分别承担不同职责
- 不新增只存在内存中的任务状态
- 不新增无法回测的独立预测算法
- 不新增 NetworkX 作为长期主图数据库；除非明确用于离线分析，否则优先使用 Neo4j 查询和已有图算法

### 11.3 三类文本的边界

为了避免内容重复，系统统一区分以下三类文本：

#### 文章摘要

回答“这篇文章讲了什么”，服务文章列表、快速阅读和全文搜索。

来源是单篇文章，通常不需要跨文档推理。

#### 知识声明

回答“这篇资料提供了什么可复用事实、观点、方法或假设”。

必须有来源和证据，可以与其他文章中的声明合并、支持或冲突。

#### 知识综合文档

回答“基于多份资料，目前对某个主题可以形成什么判断”。

必须保存来源声明、分歧、时间范围和不确定性，是后续知识回灌和决策支持的主要产物。

### 11.4 文章处理流程的统一入口

文章不再同时触发多条相互独立的增强链路。统一采用以下流程：

```text
采集/导入
    -> Article入库
    -> kg_sync同步基础实体
    -> 创建knowledge_job
    -> 知识声明流水线
    -> 跨文档关联
    -> 生成综合文档候选
    -> 审核或自动质量门控
    -> 发布到知识库和索引
```

其中：

- `kg_sync` 负责“文章是否已同步、基础实体是否完成”
- `knowledge_job` 负责“知识增强是否完成、失败如何恢复”
- `knowledge_synthesis` 负责“是否形成新的可复用知识文档”
- `forecast` 负责“预测是否准确”

这四种状态不能继续混用现有的 `Article.kg_status`。

### 11.5 现有 API 的处理策略

#### 保留并兼容

- 文章查询和导入 API
- 基础知识图谱查询 API
- 实体搜索 API
- 文章 KG 同步状态 API

#### 改造

- `/self-enhancement/process-article`：改为创建持久化知识任务，不直接等待完整处理
- `/self-enhancement/status/{id}`：读取数据库任务状态
- `/self-enhancement/knowledge-points`：改为查询知识声明，并保留旧字段映射
- `/self-enhancement/associations`：改为查询有证据的知识关系
- `/prediction/trend`：区分趋势分析和正式预测

#### 逐步废弃

- 只返回内存结果的批处理状态接口
- 只按单篇文章统计的知识点总数
- 只展示 `summary` 字段的增强结果
- 以 `kp_{article_id}_{index}` 作为永久知识 ID 的方式

### 11.6 现有数据迁移策略

不直接删除历史 `KnowledgePoint` 节点，采用三步迁移：

1. 将历史节点映射为 `knowledge_claim` 的 `candidate` 状态
2. 尝试补充来源文章和原文证据，无法补齐的标记为 `legacy_unverified`
3. 新流程稳定后，旧 API 只读兼容，停止继续写入旧格式

历史关联如果只有关键词重叠证据，则保留为 `weak_candidate`，不能直接作为正式关系使用。

### 11.7 每阶段的归并要求

每个阶段完成时必须完成对应清理工作：

- 阶段 1：统一知识点字段，禁止新旧模型同时写入两份内容
- 阶段 2：统一跨文档去重和关系写入入口
- 阶段 3：将临时 summary 替换为持久化综合文档
- 阶段 4：移除内存任务状态和重复后台触发
- 阶段 5：停止单篇文章内部关联作为正式关系的唯一来源
- 阶段 6：趋势分析只读取统一指标，不再读取实体数量作为趋势代理
- 阶段 7：预测记录统一写入 `forecasts`
- 阶段 8：前端统一展示知识声明、综合文档、审核和预测回测

## 12. 功能清晰度检查

后续代码评审必须能够用一句话解释每个模块的职责：

```text
scraper.py              获取资料
Article                  保存原始文档
article_enrichment.py   生成单篇文章摘要和基础元数据
kg_sync.py              同步文章基础实体
graph.py                访问和维护Neo4j图谱
knowledge_pipeline.py   处理知识声明和综合文档
knowledge_jobs          保存和恢复增强任务
prediction.py           计算趋势指标和可回测预测
frontend self-enhancement
                         展示统一的知识生命周期
```

如果一个模块同时负责采集、LLM总结、写图谱、发任务和生成预测，应继续拆分，避免新的巨型服务。

### 12.1 完成标准

达到以下条件，才认为完成了“去重建设”：

- 同一份原始资料只保存一份
- 单篇摘要和知识综合文档不互相覆盖
- 知识声明只有一个正式写入入口
- 知识关系只有一个正式写入入口
- 任务状态不再保存在进程内存
- `kg_status` 与 `knowledge_job.status` 各自含义清晰
- 趋势分析和正式预测使用不同数据结构
- 历史旧数据可以读取，新数据不再写入旧格式
